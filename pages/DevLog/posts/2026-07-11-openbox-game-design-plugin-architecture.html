OpenBox: A Game Design Plugin Architecture

A theory for separating game design, security, and networking contracts from the engine-specific plugins that implement them.

Entry body

The theory

  • Keep design knowledge independent from any one engine
  • Treat engine plugins as adapters instead of separate design systems
  • Define reusable skills with authority, replication, persistence, and security contracts
  • Pair human-readable documentation with small machine-readable manifests
  • Let the same design move from Unreal to S&box, Godot, Unity, or whatever comes next

Starting with the problem

I have been thinking about how to build game systems across multiple engines without rebuilding the design language every time.

The usual approach is to start with an engine and let its vocabulary shape the game. A system becomes an Unreal Actor or Gameplay Ability, an S&box Entity Component, a Godot Node, or a Unity MonoBehaviour. That is useful at implementation time, but it makes the design itself harder to carry between projects. Important decisions about authority, ownership, persistence, and security end up scattered through engine-specific code.

OpenBox is a theory for putting those decisions one layer higher.

The goal is not to hide the engine. The goal is to make the game design legible before the engine implementation begins.

Three layers

The architecture currently has three parts: a design and knowledge layer, engine adapter plugins, and shared skills.

The design layer is the engine-agnostic brain. It would hold the rules and vocabulary that should remain stable across implementations:

  • gameplay pillars
  • networking and authority rules
  • ownership and trust assumptions
  • inventory and persistence concepts
  • economy and progression rules
  • animation and presentation requirements
  • project terminology and coding standards

This is where a question such as “who is allowed to confirm this trade?” should be answered. The answer should not change just because the game is being implemented in a different runtime.

The second layer is the engine adapter. An Unreal plugin, an S&box plugin, a Godot plugin, or a Unity plugin would translate the design into the correct runtime structures. The adapter knows the engine’s APIs, lifecycle, replication model, serialization tools, and preferred patterns. It does not redefine the underlying design every time.

The third layer is the shared skill contract. A skill is a reusable unit of game behavior with enough information to describe what it needs and what guarantees it must provide.

OpenBox
├── Design
├── Security
├── Networking
├── Persistence
├── Gameplay
├── Skills
└── Runtime
    ├── Unreal
    ├── Sbox
    ├── Godot
    └── Unity

Skills as contracts

The word “skill” can mean many things in a game, so the useful part is not the name. The useful part is the contract around it.

A Trading skill, for example, should be able to describe its dependencies on Inventory and Currency. It should state that the server is authoritative, that ownership must be validated, that funds must be checked, that the important result is replicated reliably, and that the completed transaction is persisted.

That contract can then be implemented in the shape the target engine expects. The design remains the same even though the code will not.

name: Trading

requires:
  - Inventory
  - Currency

authority:
  - Server

security:
  - ValidateOwnership
  - ValidateFunds

replication:
  - Reliable

persistence:
  - Database

The manifest is intentionally small. It is not meant to replace design documents or implementation notes. It is an indexable contract that lets a tool quickly understand the system’s boundaries before opening the deeper documentation.

Why security belongs in the design layer

Security is often added after a feature exists, which usually means trying to patch trust assumptions into a system that was never designed to be authoritative.

OpenBox treats authority and security as part of the skill definition from the start. A client can request a trade, but it should not be able to decide that the trade succeeded. A player can request an inventory action, but the server still needs to validate ownership, distance, item state, and available funds. The adapter can express those checks using engine-specific APIs, while the design layer keeps the trust model visible.

This also makes review easier. A skill can be checked for missing validation before it is implemented in four different runtimes. The same design review can expose a flaw once instead of allowing four slightly different versions of the same exploit path.

What this could become

The long-term idea is an OpenBox SDK for game design rather than a single giant engine plugin. Codex could use the design layer to answer questions about the intended system, then use an engine adapter to turn that intent into implementation work.

That would make requests like these more coherent:

Implement the Trading skill in Unreal.

Port the Trading skill to S&box.

Review the Trading skill for missing authority validation.

The first request is implementation. The second is translation. The third is design and security review. They are different tasks, but they can all refer to the same source contract.

Still a theory

This is an architecture direction, not a finished framework. The difficult parts are still ahead: deciding how much belongs in a manifest, defining stable interfaces between design and runtime, handling features that genuinely do not translate cleanly, and avoiding a documentation system that becomes heavier than the games it is meant to support.

The next useful step is probably a small vertical slice rather than a broad SDK. Trading is a good candidate because it touches ownership, inventory, currency, replication, persistence, and security in one contained feature. If the contract can describe that system clearly and survive one engine implementation, the theory will have something concrete to grow from.

For now, OpenBox is the name for the boundary: design first, engine implementation second.
